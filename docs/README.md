# Software Packaging: Django (`configsite`)

## Overview
This project takes a Django application and packages it so that anyone can
reproduce the same environment and install the same artifact on another machine.
It covers a dependency manifest (`pyproject.toml`), a lockfile for exact versions,
Semantic Versioning, built distributable artifacts (a wheel and a source
distribution), environment-specific settings, and a dependency security audit.

## Environment
- Windows 11 with WSL2 (Ubuntu 24.04)
- Python 3.12.3, pip 24.0, inside a project-local virtual environment (`venv/`)
- Django 6.1.1

## Project Structure
```
django-packaging-project/
├── configsite/
│   ├── settings.py          # shared base settings
│   ├── settings_dev.py      # development overrides
│   ├── settings_prod.py     # production overrides (secrets come from the environment)
│   ├── urls.py, wsgi.py, asgi.py

├── docs/                    # this README
├── screenshots/             # evidence of each step
└── scripts/
```

## Task 1: Dependencies (`pyproject.toml`)
Dependencies are declared as **ranges**, not single versions:

```toml
dependencies = [
    "Django>=6.1,<7.0",
    "asgiref>=3.12,<4.0",
    "sqlparse>=0.6,<1.0",
]
```

**Why ranges.** Pinning one exact version means you never receive security or bug
fixes. Leaving a package unconstrained means a future major release could silently
break the app. A range like `>=6.1,<7.0` sits between those extremes. It relies on
Semantic Versioning's promise that a major version bump is where breaking changes
happen, so anything inside the `6.x` line is safe to accept.

`asgiref` and `sqlparse` are **transitive dependencies**: I never asked for them
directly, Django needs them. They are listed explicitly so the manifest matches
what is actually installed.

## Task 2: Reproducibility (the lockfile)
Ranges say what is *acceptable*. A lockfile says what is *exact*. Two installs
made six months apart from the same ranges could get different Django versions,
so `pip-compile` (from `pip-tools`) generates `requirements.lock.txt`:

```bash
pip-compile pyproject.toml -o requirements.lock.txt
```

The output pins every package, including transitive ones, and its `# via`
comments record why each package is present (for example, `asgiref` is there
because `django` requires it).

**Verification.** I created a brand-new empty virtual environment, ran
`pip install -r requirements.lock.txt`, and `pip list` showed identical versions
to my development environment. That is the proof that the lockfile alone is enough
to rebuild the environment.

**Limitation to be aware of.** The lockfile header shows `--no-index`, so it locked
what was already installed locally rather than resolving against the live package
index. For three packages that is equivalent. A fully independent lock would
resolve against PyPI.

## Task 3: Versioning strategy (Semantic Versioning)
Versions follow `MAJOR.MINOR.PATCH`:

| Bump | When | Example |
|---|---|---|
| PATCH | Bug fix, no change in how it is used | 0.2.0 to 0.2.1 |
| MINOR | New functionality, existing usage unaffected | 0.1.0 to 0.2.0 |
| MAJOR | Breaking change | 0.3.0 to 1.0.0 |

Lower numbers reset to zero when a higher one is bumped.

The project stays on `0.x` on purpose: under SemVer, major version `0` means
"initial development, anything may change". A `1.0.0` release would be a promise of
backward compatibility that this project is not ready to make.

The version history here:
- **0.1.0**: initial Django project with the dependency manifest.
- **0.2.0**: added the `core` app (new functionality, nothing broken).
- **0.3.0**: added separate dev and prod settings, and rebuilt the artifacts. The
  0.2.0 wheel had been built before those files existed, so it did not contain
  them, which is why a new build and version were needed.

## Task 4: Build artifacts
```bash
pip install build
python -m build
```

`python -m build` reads the `[build-system]` section of `pyproject.toml`
(setuptools as the backend) and produces two files in `dist/`:

- **`configsite-0.3.0.tar.gz`**: the *source distribution*. It is the source code
  packaged up and still needs a build step on the installing side.
- **`configsite-0.3.0-py3-none-any.whl`**: the *wheel*, the pre-built format that
  `pip` prefers. The filename encodes `py3` (any Python 3), `none` (no ABI
  requirement) and `any` (any OS or architecture), because this project has no
  compiled code.

**Package discovery fix.** The first build failed with `Multiple top-level packages
discovered in a flat-layout: ['core', 'configsite', 'screenshots']`. setuptools
guesses which folders are code, and it treated my evidence folder as a package. I
fixed it by stating the packages explicitly instead of letting it guess:

```toml
[tool.setuptools.packages.find]
include = ["core*", "configsite*"]
```

**Verification.** I installed the wheel into a fresh virtual environment. `pip`
read the dependency constraints from the wheel's own metadata, installed Django,
asgiref and sqlparse automatically, and `pip list` showed `configsite` as an
installed package in its own right.

**Note on committing `dist/`.** In a production repository, build output is normally
gitignored and published to a package registry. The `dist/` folder is committed
here deliberately, because the assignment asks for the generated artifacts as
evidence.

## Task 5: Environment-specific configuration
Configuration is split so that development values are never hardcoded into
production:

- `settings.py`: the shared base.
- `settings_dev.py`: imports the base, sets `DEBUG = True` and localhost hosts.
- `settings_prod.py`: imports the base, sets `DEBUG = False`, reads `SECRET_KEY`
  and `ALLOWED_HOSTS` from environment variables, and enables HTTPS hardening
  (`SECURE_SSL_REDIRECT`, secure session and CSRF cookies, HSTS).

Django chooses the module through the `DJANGO_SETTINGS_MODULE` environment
variable, for example:

```bash
DJANGO_SETTINGS_MODULE=configsite.settings_dev python manage.py check
```

**Why environment variables.** The secret key signs sessions and tokens, so anyone
holding it can forge them. It must never be committed. `settings_prod.py` reads it
with `os.environ[...]`, so a missing value stops startup with a `KeyError`. This is
the same fail-fast idea as `set -u` in Bash, and I confirmed it: running the prod
settings with no secrets failed immediately.

**Production audit (`check --deploy`).** After the hardening changes the audit went
from six findings to three. What remains, and why:
- `security.W005` (HSTS include-subdomains) and `security.W021` (HSTS preload) are
  deliberately left off. They commit a domain and all its subdomains to HTTPS-only
  and preload is hard to reverse, so they should only be enabled once a real domain
  is known to serve HTTPS everywhere.
- `mail.E001` (development email backend) is out of scope because this project
  sends no email. A real deployment would configure an SMTP backend.

`SECURE_HSTS_SECONDS` is set low (3600) on purpose: browsers remember HSTS for that
long, so a large value set before HTTPS works could lock users out.

## Task 6: Verification and dependency audit
- `python manage.py check` passes under the dev settings.
- `pip-audit -r requirements.lock.txt` reports **No known vulnerabilities found**
  for the pinned versions.

## Troubleshooting Log
| Problem | Cause | Fix |
|---|---|---|
| Folders named `docsmkdir`, `screenshotscd`, `scriptsmkdir` | Commands chained with `/` instead of `&&`; `/` is a path character, not a separator | Removed with `rmdir`, recreated with `mkdir -p docs && mkdir -p screenshots && mkdir -p scripts` |
| Duplicate `configsite/configsite/` and `configsite/manage.py` | `startproject` had been run twice | Removed the nested copy, confirmed with `python manage.py check` before committing |
| `Multiple top-level packages discovered` on build | setuptools auto-discovery treated `screenshots/` as a package | Explicit `[tool.setuptools.packages.find]` include list |
| 0.2.0 wheel missing the env settings | Artifact was built before those files were created | Bumped to 0.3.0 and rebuilt; checked the wheel contents with `unzip -l` |
| `pip-compile` warning about `--strip-extras` | Upstream default changes in a future version | No action needed; lockfile output was unaffected |
